# من الفكرة إلى تطبيق منشور — الـ Workflow

مبني على المراحل اللي ظهرت فعلًا في المشروع (audit → fix → refine → اتجاهات → تنفيذ → تعميم → تشغيل). **الخطوات بتتحرك فقط لما معيار الخروج يتحقق بدليل.**

## Intake checklist (قبل أي كود — لازم تتجاوب كلها أو تتسجّل كـ "ناقص")
- [ ] **الهدف:** إيه التطبيق ولمين، وإيه الإجراء الواحد الأهم فيه؟ (جملة واحدة)
- [ ] **المتطلبات:** قائمة مرقمة بالنتيجة المرئية، مصنّفة (مطلوب الآن / بعدين)
- [ ] **التقنيات:** frontend / backend / قاعدة بيانات / auth / استضافة — لكل واحدة: مختارة (ليه) أو غير محددة. لا تنسخ تقنيات مشروع تاني بدون سبب
- [ ] **الاعتماديات الخارجية:** حسابات، API، دفع، تتبّع/إعلانات (ولو فيه إعلانات: انسخ `optional/rules/tracking-and-ads.md`)
- [ ] **القيود:** لغة/اتجاه (RTL؟)، أجهزة، أداء، ميزانية، ممنوع المساس
- [ ] **البيانات والأصول:** إيه الحقيقي المتاح؟ إيه الناقص (صور/نصوص/لوجو)؟ مفيش اختلاق
- [ ] **معايير القبول:** لقطات/مقاسات/سلوكيات قابلة للقياس
- [ ] **سياسة التسليم:** الفرع، مين بيوافق على الدمج/النشر، هل في نشر أصلًا
- [ ] **الافتراضات والأسئلة المفتوحة:** مكتوبة، والمستخدم وافق أو أجاب

| # | المرحلة | الـ Skill | معيار الخروج |
|---|---|---|---|
| 0 | تهيئة: انسخ الـ kit، أنشئ `projects/<name>/NOTES.md`، اسأل: سياسة الدمج، المناطق المحمية، لغة التقرير، الجهات (موبايل/ديسكتوب) | — | NOTES.md ممتلئ |
| 1 | الفكرة ← متطلبات | `brief-to-requirements` | قائمة متطلبات مرقمة + قائمة "ممنوع المساس" + معايير قبول، **والمستخدم وافق** |
| 2 | اتجاه التصميم | `design-direction` | المستخدم اختار mockup + لوحة ألوان بالاسم |
| 3 | البنية والتقنية | (من الـ Intake checklist؛ مفيش تقنية افتراضية) | تقنية مختارة مع سبب، وما اتجرّبش مُعلَّم |
| 4 | بناء الواجهة | `ui-build` | الصفحات الأساسية شغّالة ببيانات حقيقية |

| 7 | إصلاحات | `fix-and-verify` | سبب جذري مثبت + تحقق |

| 9 | نشر وتحقق حي | `ship-and-verify` | marker حي + اختبار على الحي |
